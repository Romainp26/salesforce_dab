## 1. Executive summary

**Verdict: the normal nightly path is coherent and well built, but the bundle is not ready to hold PII in PROD.** Idempotent SCD2 MERGE, watermark-after-commit, per-object failure isolation, append-only ops tables, and casts that never put values in logs all trace correctly, and the 85 tests pass. The design breaks when the encryption policy changes, at the edges of the encryption scope, and wherever the bundle relies on platform permissions it doesn't define.

Top risks:
1. **Encrypting an existing column doesn't remove its plaintext (S2, Critical, Reproduced).** Plaintext stays readable through time travel. It also stays in active data files after `VACUUM`, because the tables use deletion vectors, and in the per-file min/max statistics in `_delta_log`. Nothing in the code or runbook purges it.
2. **`_row_hash` is an unsalted SHA-256 of the plaintext row, PII included (Critical, Reproduced).** It is stored next to the ciphertext. I recovered an encrypted phone number from it with a 100k-candidate brute force. The runbook gives BI and data science SELECT on these tables.
3. **PII leaks around the encrypted columns (Critical, Verified).** Five History objects of PII objects store `OldValue`/`NewValue` in plaintext. Contact `Name` is encrypted while `FirstName`, `LastName`, `Birthdate` and `Passport_Number__c` are not.
4. **One secret scope per environment holds both the AES key and the Salesforce JWT key, and the design grants `pii_readers` READ on it (Critical).** A PII reader can then act as the integration user, and can decrypt Kumka too, because the entities share one key.
5. **Hard deletes are never detected on 122 of 124 objects (Critical by your rubric; the design accepts it in D-18).** A full recycle bin or a hard-deleting archival process leaves deleted records current, silently.
6. **There is no supported way to change the policy (High, Reproduced).** Decrypting a field leaves a mixed ciphertext/plaintext column that the DQ check stops looking at. Encrypting a non-STRING column fails that object every night. A numeric scale change rounds values silently, with no warning.
7. **A missing or inaccessible object is "skipped" and the job stays green (High).**

**Most valuable next action, before go-live:** split the secret scopes, key `_row_hash` with a secret, and write a tested "PII policy change" job: re-encrypt or decrypt, retype, `REORG … APPLY (PURGE)`, `VACUUM` with a deliberate retention, then verify with time travel. Also enforce history encryption from the parent object's PII list.

### 2b. Part 1 structural review: notes per area

**Bundle structure.** One bundle with `include: resources/*.yml`, a wheel artifact (`uv build`), and three jobs plus alerts and a dashboard for Roojai only. The catalog is never a variable: it is derived in code (`config.py:167`) and interpolated as `roojai_th_${bundle.target}` in the alerts and dashboard (`resources/sf_ops.alerts.yml:10, 34`). That is consistent but locks the naming. The secret scope names live in `config/entities.yml:37-42`, not in target variables. No secrets are hard-coded: grep found only test keys in `tests/conftest.py`. Many TODO placeholders remain (host, SP IDs, policy IDs, warehouse, emails, scopes, org usernames); validate can't catch any of them.

**Environment parity.** Targets are only `uat` and `prod`. There is no dev (F-21).
- Intentional differences: SP, cluster policy, secret scope, org domain and user, and `paused: [uat]` on Contract and Payments__c.
- Unintentional sameness: one warehouse placeholder, one alert address, the same schedule, the same `pii` block (whether UAT and PROD keys differ is unknown).
- UAT is `default: true` and `mode: production`.

**Identity and permissions.**
- Jobs run as the target's SP (`databricks.yml:79-80, 88-89`) on a `SINGLE_USER` cluster as that SP with local disk encryption (`:56-60`).
- **Who can read the encryption key:** the SP; anyone granted READ on the environment scope, which the design gives to `pii_readers` (F-04); workspace admins, who have MANAGE on all scopes by default (Inferred); Azure principals with get-secret on the Key Vault (outside the repo).
- **Who can read plaintext:**
  - the SP;
  - catalog owners and metastore admins (landing volume, time travel, deletion-vector residue: F-01, F-18; Inferred UC semantics);
  - `pii_readers` through `decrypt_pii`;
  - anyone with SELECT on `bronze_salesforce_scd2`: History plaintext (F-03), unencrypted personal fields (F-09), the `_row_hash` oracle (F-02), time travel after S2 (F-01);
  - operators with SELECT on `ops_salesforce`, through any runbook §5.9 backup clone placed there;
  - initial-load engineers on `backup_salesforce`;
  - anyone holding the JWT key, directly in Salesforce.
- No UC grant other than `decrypt_pii` EXECUTE is in code (F-24).

**Job design** (`resources/sf_nightly.job.yml`).
- Order: preflight → ingest → views → dq → cleanup. views, dq and cleanup run `ALL_DONE`; cleanup depends on every task, so it always runs (`:93-100`).
- Per-task timeouts (6 h / 1 h), `max_concurrent_runs: 1`, an `on_failure` email, and no task retries: recovery is a manual repair.
- **One failing object doesn't stop the run:** the others finish and the task raises at the end (`tasks.py:529-549`). Verified and tested.
- Gaps:
  - skipped objects leave the job green (F-10);
  - no duration or health alerts;
  - backfill, seed and nightly runs can overlap on the same tables (only documented);
  - a cancelled run skips cleanup (F-18).

**Configuration model.** Object policies sit in YAML validated at load: unknown keys, enum values and duplicates fail, and PII objects must use `require-approval` (`config.py:204-258`). The field allowlist is seeded into `ops_salesforce.field_allowlist` and evolves at run time. Gaps:
- PII names, `when` rules and History coverage are not validated against Salesforce (F-03, F-15, F-19);
- no classification record (F-09);
- runtime-only approvals (F-16, F-25).

**State management.**
- Watermarks are append-only (`watermark_history`), read through a max view (`ops.py:80-85, 161-176`). They advance only after `load_object` returns, so after the MERGE commits (`tasks.py:357-363`). Not atomic with the MERGE, but a crash in between replays as a no-op, which is safe.
- `encryption_state` combined with a Delta commit tag makes re-encryption crash-safe (tested).
- `run_events` is append-only per stage, and `run_log` is a view.
- The `run_plan` is per run, so a repair reuses the original preflight's field list.

**Idempotency.**
- Source rows are deduped per `Id` (latest watermark, then latest page).
- The MERGE matches on `Id` and `_is_current`, with a keyed and an unkeyed copy of each changed row, so the MERGE can never see two source rows for one target row.
- A new version is written only when the watermark is newer *and* the hash differs (`scd2.py:120-123, 163-218`).
- Replays and the 1-hour overlap are no-ops (tested: `test_changes_overlap_and_replays`, and re-run in UAT checklist §4).
- The flip side: equal-watermark corrections are impossible (F-12).

**Observability.**
- Per-object events with counts, Bulk job IDs, watermarks before and after, and errors.
- Audit columns: `_run_id`, `_extracted_at`, `_page_no`, `_pii_key_version`. There is no source-system column, by design (one org per catalog).
- DQ: one current row per Id and ciphertext shape (critical); COUNT reconciliation, watermark advance, drift, certificate and landing leftovers (warnings, alerted at 07:00 as a count).
- Missing: freshness, completeness against the Bulk `numberRecordsProcessed`, and per-object volume anomalies.

**Tests.**
- 85 pass. They cover config counts, auth key formats, Bulk paging and retries, WHERE clauses, SCD2 versioning, deletes, archival, History, views, DQ, the seed, preflight isolation, repair skip, and backfill.
- They use literal keys instead of `secret()`, and UC-only statements (volume, function, grants) never run.
- Not covered:
  - S1 decrypt;
  - S2 on non-STRING types, and residue in history, DV files and log stats;
  - History objects of PII parents;
  - hash leakage;
  - precision/scale retypes;
  - concurrent jobs;
  - cancelled-run cleanup;
  - a real Salesforce contract (Bulk responses are mocked with `responses`).
- Several tests pin config counts (124, 29, 5767), which is the current implementation rather than a stated guarantee.

## 3. Scenario walkthroughs

### S1. An encrypted field must become plaintext
**(a) Today.**
- **New loads only.** `encrypt_columns` encrypts only listed fields (`encrypt.py:137-139`). The existing column keeps its type, because `ensure_table` only adds missing columns (`scd2.py:95-101`), and `types` comes from the table, so new plaintext is written as STRING. Reproduced: version 1 holds ciphertext, version 2 holds `0899999999`. The column is mixed.
- **No decrypt path.** The backfill only encrypts and only touches current versions (`scd2.py:353-397`). A full reload rewrites nothing for unchanged records (F-12). A reset (runbook §5.9) drops history.
- **Type:** stays STRING forever, with no schema evolution, even for dates and numbers.
- **Consumers:** the view passes the mixed column through. `decrypt_pii` raises `AES_CRYPTO_ERROR` on plaintext values (reproduced), so a decrypting query fails. Joins on ciphertext silently stop matching across the change date.
- **DQ** no longer checks the column, because `pii_predicates` follows the config (`encrypt.py:118-127`).
- **Re-adding it later** never encrypts the plaintext in between (`scd2.py:229-230`); DQ then fails every night (reproduced).

**(b)** Incorrect: a silently mixed column, and no reversible path.

**(c) Blast radius:** every version of the object's SCD2 table, its view, every consumer calling `decrypt_pii` on the column, and joins and groupings on it. History objects are unaffected unless the field is in `history_encryption`.

**(d) Fix:** a decrypt migration job, `UPDATE t SET col = try_decrypt(col) WHERE is_ciphertext(col)`, then retype (F-06 mechanics), delete the `encryption_state` row, and record the change. Validation should refuse removing a field from config without that migration. Test T1.1–T1.3.

### S2. A plaintext field must be encrypted across the whole table
**(a) Today.**
- **Current snapshot:** at the object's next load, `apply_new_encryption` runs one `UPDATE … WHERE col IS NOT NULL` (plus the `when` rule) over every version (`scd2.py:221-248`, `encrypt.py:158-170`). New and updated rows are encrypted by `encrypt_columns`.
- **Exceptions:**
  - it runs only if the object has extracted rows that night (F-14);
  - it fails on non-STRING columns (F-06);
  - `_row_hash` keeps the plaintext fingerprint (F-02).
- **Recoverability (reproduced on Delta 4.3):**
  - **Time travel:** `VERSION AS OF <pre-update>` returns plaintext, for at least the 7-day default `deletedFileRetentionDuration` (`docs/runbook.md:231`).
  - **Deletion vectors** (`scd2.py:91`): partially updated files stay active, with the plaintext rows masked by a DV. `VACUUM` doesn't remove them; only `REORG TABLE … APPLY (PURGE)` followed by `VACUUM` does. Predictive optimization may compact some files but promises no purge (Inferred).
  - **Transaction log:** per-file `minValues`/`maxValues` stats of the column, plaintext in old commits, persist until log cleanup (default 30 days, plus checkpoints). VACUUM and REORG don't touch the log.
  - **Change Data Feed:** not enabled (no `enableChangeDataFeed` anywhere), so not a path unless someone enables it.
  - **Clones:** runbook §5.9 suggests a DEEP CLONE into `ops_salesforce`, readable by operators per §6. `backup_salesforce` holds plaintext for every field Synapse didn't encrypt.
  - **Downstream copies:** none inside the bundle; external silver copies can't be determined.
- **Logs, error tables, quarantine:** no quarantine or error tables exist, and logs hold counts and IDs only (verified: no `show()`, `display()` or `print()` in `src/`; cast errors are counted, never echoed). Plaintext sits in landing CSVs until deleted (F-18), and possibly in storage soft delete (Inferred).
- **MERGE, join and partition keys:** nothing prevents encrypting `Id`. The MERGE would still work, because encryption is deterministic, but the hard-delete check compares plaintext landed Ids with ciphertext Ids and would flag every User and GroupMember record (F-19). Tables are liquid-clustered on `Id` with no partition column. Encrypting a field the conditional rule reads breaks the rule (F-19). Deterministic encryption *is* needed for joins and grouping. Old values re-encrypted in place must use the same text form as new loads (raw Salesforce string), or equal values won't match; that matters for typed columns (F-06).

**(b)** The current snapshot is correct for STRING columns. The full-table guarantee fails: plaintext stays recoverable.

**(c) Blast radius:** the SCD2 table's storage, its log and time travel; its History table if the field is tracked (F-03); `backup_salesforce`; any clones; storage soft delete. Views are not affected.

**(d) Fix:** a policy-change job (F-01 recommendation), with ordered steps and verification queries. Test T2.1–T2.6.

### S3. Other encryption cases
- **Key rotation.**
  - (a) Not automated. The runbook's manual UPDATE uses one key for all rows. `_pii_key_version` is written per row (`scd2.py:321`) and per state row, but nothing reads it, and `decrypt_pii` knows one key (`ops.py:116`).
  - (b) Inadequate.
  - (c) Every PII column in every catalog that shares the key (both entities).
  - (d) F-17.
- **Missing or inaccessible key.**
  - (a) JWT secrets are read in preflight (`tasks.py:74-89`), so a missing scope fails the whole job up front. The AES key is read lazily inside SQL through `secret()` (`encrypt.py:34-38`); preflight creates `decrypt_pii` without evaluating it. So each PII object fails at load, after its extract; non-PII objects load. The code never falls back to plaintext. (That `secret()` raises on a missing scope or key is Inferred, since tests substitute literals.)
  - (b) Safe, but late: there is no up-front key check, and no check that the key decodes to 32 bytes. A 16- or 24-byte key would be accepted by `aes_encrypt`, silently weaker.
  - (d) In preflight, run `SELECT length(unbase64(secret(...)))` and require 32, and check the IV is 16.
- **Null or empty.**
  - (a) Nightly: `''` becomes null before encryption (`transform.py:47-51`), and `aes_encrypt(NULL)` is NULL (tested). The DQ check skips nulls. The seed doesn't normalise, so a backup `''` becomes ciphertext of `''` (F-26).
  - (b) Mostly consistent, except the seed.
- **Bronze vs silver.** There is no silver layer in the bundle. Views pass the SCD2 columns through, so whatever the table holds (mixed, plaintext History) propagates to consumers. `decrypt_pii` returns STRING for every type. Downstream silver tables are outside the repo and can't be assessed.

### S4. Objects missing in UAT (license, package, custom object)
**(a) Today.**
- **Detection:** before querying. `describe_all` collects a 404 per object (`metadata.py:57-83`), and preflight records `skipped` with "not in the uat org" plus an `object_planned` warning, unless the object is paused in that environment (`tasks.py:189-214`). Tested.
- **Effect:** one missing object never fails the job; it's skipped with a warning. Other describe errors count as failed and fail the job at the end.
- **Partial vs full success:** the job status can't tell them apart (green). `run_log` and the 07:00 warning alert can.
- **Missing vs zero rows:** distinct. Missing is skipped at preflight. Zero rows on an incremental object just skips the load. Zero rows on a full-load object fails the object instead of flagging everything (`tasks.py:387-388`, `deletes.py:30-31`, tested).
- **Per-environment inclusion:** supported (`paused: [uat]`), logged as skipped, with no warning.

**(b)** Correct for UAT. Wrong for PROD, where an access loss also returns 404 (F-10).

**(c)** The object's table and view go stale with no indicator; consumers can't tell.

**(d)** Set expected absence per environment (`paused` or `expected_missing`), make unexpected 404s fail, add freshness. Test T4.1–T4.3.

### S5. The object exists but a field doesn't (not deployed, or hidden by FLS)
**(a)** Describe returns only the fields the integration user can read, so the field is not planned (`metadata.py:98-110`) and the SOQL never fails. On the first run, with no previous snapshot, there's no warning at all. Later, a `field_removed` warning appears if the field is allowed, and new versions hold null while old versions keep their values. If the field disappears between preflight and extract, the SOQL fails with `INVALID_FIELD` and the object fails.

**(b)** Silent nulls; only a warning.

**(c)** The column in SCD2 and the view: values "disappear" in new versions.

**(d)** F-23. Test T5.1.

### S6. Schema drift
**(a)**
- **New field:** on `auto-add` objects (113) it is queried, added with `ALTER TABLE ADD COLUMNS` and stored unencrypted the same night, with a digest warning. On `require-approval` objects it waits as pending (`metadata.py:98-110`).
- **Deleted field:** the column stays and is null from then on, with a warning.
- **Retype:** compared on `sf_type` only.
  - text→picklist: no-op (STRING stays STRING).
  - number precision or scale change: not detected. Scale up rounds silently; precision up overflows, so the object fails nightly until a reset (F-08, reproduced).
  - number→text: the object fails at the cast check.
  - text→number: values stay strings.
  - date↔datetime: silently wrong (reproduced).
- **Rename:** seen as a removed field plus a new one, with no lineage. On a PII object the new name waits for approval; on an auto-add object it lands in plaintext.

**(b)** Detection is partial, and the silent precision loss is incorrect.

**(c)** Affected columns in SCD2 and views; for renames, any consumer of the old column name.

**(d)** F-08, F-16, F-23. Test T6.1–T6.4.

### S7. Deleted records
**(a)** `queryAll` is used for Bulk (`bulk.py:111-115`) and REST (`extract.py:149`). `IsDeleted` and `LastModifiedById` are always queried (`metadata.py:19, 102`).
- **Soft delete:** a new version with `_is_deleted` (or `_is_archived` for archival users, `scd2.py:138-154`).
- **Undelete:** a new version with both flags false.
- **Views:** `retain` shows soft-deleted records with `IsDeleted = true`; `delete` hides them; full-load objects hide hard deletes (`views.py:31-38`).
- **Hard deletes and recycle-bin purges:** checked only on User and GroupMember, by absence from the full extract (`deletes.py`). Every other object keeps the record current (F-05).
- **History rows** deleted later are never updated (F-31).

**(b)** Correct for soft deletes; unsafe for hard deletes.

**(c)** Every incremental table and its view, plus counts and joins downstream.

**(d)** F-05 reconciliation. Test T7.1–T7.4.

### S8. Incremental logic
**(a)**
- **Watermark:** `SystemModstamp` (default; D-12) or `CreatedDate` for History (`config.py:224`).
- **Window:** `wm > stored − 1h AND wm <= now`, both in UTC, to the second (`extract.py:34-35, 56-61`). The overlap absorbs late commits; replays are no-ops.
- **Formula fields and rollups:** formula drift is accepted (D-25), and a full reload can't fix it (F-12). Whether rollup recalculation touches SystemModstamp can't be determined from the repo.
- **Timezones:** watermarks are UTC NTZ; data is +7 h NTZ (tested).
- **Failed write:** the watermark doesn't advance (`tasks.py:357-363`). A truncated but "successful" extract does advance it (F-13). Two changes in one second: the second is dropped (F-31).

**(b)** Sound, except completeness and corrections.

**(c)** Incremental objects.

**(d)** F-12, F-13. Test T8.1–T8.4.

### S9. Volume and limits
**(a)**
- **APIs:** Bulk 2.0 everywhere, except `api: rest` (ContractStatus, TaskStatus). An automatic REST fallback applies only when Bulk rejects the object at job creation (`extract.py:153-172`).
- **Memory:** pages stream to files (100k records each), so memory stays flat.
- **Retries:** 5 attempts on 429/5xx; one re-authentication on 401; a dropped page download is fetched again by locator; a job is aborted after 3 h (`bulk.py`). `QUERY_TIMEOUT` and API-limit errors fail only that object.
- **API limits:** no pre-check (the design says API usage is not a constraint).
- **Split reload:** `split_full_reload` is set on no object.
- **Compound and binary fields:** compound address and location fields, and base64 fields, are skipped (`metadata.py:17`); their components are queried if allowlisted.
- **Sizing:** the single node (4 cores, 16 GB) is unproven for first full loads (Q6). DQ cost grows with history (F-22). Whether Bulk supports the feed and Process objects is open (Q3).

**(b)** Reasonable for steady state; unproven at scale.

**(d)** Run a UAT first-load benchmark; F-13, F-22.

### S10. Duplicates
**(a)** Duplicate Ids within a batch: the latest watermark wins, then the latest page (`scd2.py:120-123`). A retried page overwrites the same file (`bulk.py:173-193`). Split ranges are disjoint. Overlapping windows are no-ops. The MERGE source holds at most one keyed row per Id, so "multiple source rows matched" can't occur. The backfill dedupes; History uses an anti-join plus `NOT MATCHED` only.

**(b)** Correct. Verified, and tested (`test_changes_overlap_and_replays`).

**(c)** None.

**(d)** Keep the DQ check `one_current_row_per_id` (critical).

### S11. Adding or removing an object
**(a)**
- **Add:** with no watermark, the first run extracts everything (`extract.py:58-61`), then it goes incremental. A `require-approval` object with no allowlist rows has every field pending, so preflight fails it with "Id must be … allowlisted" (loud). An `auto-add` object with no rows auto-adds every field, PII included, unencrypted.
- **After the seed:** an added object gets no Synapse history.
- **Remove:** the table, view and ops rows stay, the view serves frozen data, and nothing flags it (F-20).

**(b)** Initialisation is correct; removal is unsafe for consumers.

**(d)** F-20; require `require-approval` for new objects until they're classified (F-09). Test T11.1–T11.2.

### S12. Re-runs, concurrency, backfill windows
**(a)**
- **Repair:** objects with an `ingest/succeeded` event are skipped; failed ones re-extract from their committed watermark (`tasks.py:486-496`). Safe and tested.
- **Two runs of one job:** blocked by `max_concurrent_runs: 1`.
- **Nightly + backfill + seed:** no lock between them. Concurrent MERGEs or UPDATEs on the same table conflict and one fails (documented). The seed racing an unpaused nightly is F-11.
- **Historical window:** not possible. Watermarks only move forward (`ops.py:80-85`), `full_reload` can't rewrite equal watermarks (F-12), and a reset loses history.

**(b)** Retry is correct; historical backfill is unsupported.

**(d)** A catalog-level run lock (an ops row checked in preflight), and F-12. Test T12.1–T12.3.

### S13. Credential expiry or connection failure mid-run
**(a)**
- **Auth fails in preflight:** the job fails, `ingest` doesn't run, and `views`, `dq` and `cleanup` still run.
- **Mid-run:** Bulk refreshes once on a 401 (`bulk.py:97-101`); REST errors fail the object.
- **Cleanup of a failed object:** an extract error means no load, the watermark unchanged, and the landing folder removed in `finally` (`tasks.py:415-430`).
- **Crash after commit:** MERGE committed but watermark write failed → a no-op replay. Re-encryption UPDATE committed but state write failed → the commit tag prevents double encryption (tested).
- **Process killed:** if the driver or job dies, cleanup doesn't run (F-18).

**(b)** State stays consistent.

**(d)** Detect a cancelled run in the next preflight and clean up then. Test T13.1–T13.2.

### S14. Promotion from UAT to PROD
**(a)**
- **Derived per target:** catalog, SP, scope, and org via `--env ${bundle.target}`.
- **Org-specific IDs in config:** Contract `soql_filter` Id, the Account exclusion Id, `archival_user_ids` (PROD IDs; full and partial sandboxes copy them, developer sandboxes don't).
- **Per-catalog run-time state:** approvals, allowlist and `encryption_state` don't promote (F-25).
- **Workspace and deploy:** UAT and PROD share one workspace; `root_path` is under the deployer's user folder (F-24); CI is missing (Q10).
- **Sandbox refresh:** it invalidates UAT watermarks (runbook §5.11).

**(b)** Mostly correct; the gaps are run-time state and paths.

**(d)** Approvals through PRs; deploy from CI as an SP.

### Further scenarios found while reading the code
- **A1. Seed vs schedule race** (F-11).
- **A2. Hash oracle** (F-02).
- **A3. JWT key in the readers' scope** (F-04).
- **A4. Quiet objects never re-encrypted** (F-14).
- **A5. Rule and system-field encryption** (F-19).
- **A6. Plaintext in Delta stats.** Even when the encryption config never changes, the log holds only ciphertext stats, which is fine. After any S2 change, the stats of older commits are a third residue path beyond time travel and DV files (part of F-01).

## 5. Open questions (business decisions or information not in the repo)

1. **PII classification** (F-09): are Contact `FirstName`, `LastName`, `Birthdate`, `Identification_Number__c` and `Passport_Number__c`; Account `MiddleName`, `PersonBirthdate`, `Passport_Number__pc`, `Modified*` and `*_Formula__pc`; Case `Contact*`/`Supplied*`; Claim__c addresses and phones; and Lead personal data in scope for encryption? Who owns that list?
2. **Field history tracking:** which fields of Claim__c, Payments__c, Vehicle_Inspection_Data__c, AWSConnectOutboundCallList__c, Opportunity and Account are tracked? (Decides the real exposure of F-03.)
3. **Archival process (D-23):** do the archival users soft-delete (recycle bin) or hard-delete (Bulk `hardDelete`, `emptyRecycleBin`)? How many records a day? Does the recycle bin overflow (purge before 15 days)?
4. **Secrets (Q4):** does `secret()` inside a UC SQL function need READ on the scope from the *caller*? If so, readers need a scope that holds only their AES key (F-04). Are the UAT and PROD AES keys different? Should Roojai and Kumka share a key at all?
5. **Retention and erasure:** how long must plaintext be unrecoverable after an S2 change: hours, days? That sets `deletedFileRetentionDuration`, `logRetentionDuration` and the storage soft-delete settings. There is still no erasure policy (design: Erasure).
6. **Storage:** is blob soft delete or versioning enabled on the UC managed location of `roojai_th_*`? Who owns the catalogs, and who are the metastore admins?
7. **Grants:** who will actually have SELECT on `bronze_salesforce_scd2` (runbook §6 says BI and DS)? That decides F-02's exposure.
8. **Hard deletes (D-18):** is "never happens" verified with the Salesforce admins (Data Loader hard delete, Apex `emptyRecycleBin`, merges past 15 days)?
9. **Formula and rollup drift (D-25):** which consumers rely on formula or rollup values? Does rollup recalculation update SystemModstamp in these orgs? Unknown from the repo.
10. **Silver and downstream:** do downstream jobs materialise decrypted or ciphertext copies? They inherit every S1/S2 problem and aren't in this repo.
11. **CI/CD (Q10)** and the CLI version: which `databricks` CLI deploys, and does CI run `pytest` before deploy? (The static PII-name test is the only guard for F-15.)
12. **Sizing (Q6):** first full-load duration and memory for the largest objects on a 16 GB single node.
13. **Dev environment:** where will engineers test policy changes without touching the UAT org and catalog?
